01 · HOSPITALITY

Zeeshan Bistro

A restaurant landing page that turns a simple signup exercise into a fuller, responsive browsing flow.

Open the demo ↗

Starting point

The source exercise had a restaurant theme and a reservation form that pointed to a missing server-side file. This version keeps the concept and makes the page self-contained: visitors can explore the menu and story, then try a reservation request.

How the interaction works

The form uses labelled native inputs and browser validation. JavaScript sets the earliest reservation date to today and intercepts submission to show a local confirmation. The small-screen menu button opens and closes the navigation.

Frontend concepts

  • Semantic sections and in-page navigation make a single page easy to scan.
  • Responsive CSS reshapes the content for narrow screens.
  • Form labels and required fields connect instructions to the controls and use built-in validation.

Limits and next step

No reservation reaches a restaurant or server. A production version would send validated data to a booking service, show server responses, and protect contact details. The current success message is only a browser demo.

02 · COMMERCE

Astic Studio

A boutique storefront for practising product browsing, small pieces of UI state, and a shopping-bag flow.

Open the demo ↗

Starting point

The original folder included a fashion-store concept. This version keeps the product-browsing idea and adds a small sample catalogue, category filters, text search, favourites, and a cart drawer.

How the interaction works

The product list is held in a JavaScript array. Rendering filters that list by the selected category and search text. Cart quantities and favourite IDs are saved separately in localStorage; a guarded read falls back to empty state if saved data is missing or invalid. Quantity controls recalculate the subtotal from the sample products.

Frontend concepts

  • One product data list feeds the cards and cart totals, reducing repeated markup.
  • Event delegation handles clicks on product cards that are re-rendered after filtering.
  • Native dialog methods provide the cart drawer’s open and close behavior.
  • Storage lets state survive a refresh in the same browser, but not move to another device.

Limits and next step

Names, products, and prices are sample data. There is no inventory, account, order, payment, or server. Checkout intentionally explains this instead of pretending to process an order. A real store needs a secure backend and payment provider; product photography also needs confirmed publishing rights.

03 · AGRICULTURE

CropWise

A field-planning interface that demonstrates a form-driven result, safe text rendering, and local notes.

Open the demo ↗

Starting point

The earlier crop-advisory prototype called an AI endpoint with an empty key and inserted returned markup into the page. This demo removes the unreliable service dependency and makes its sample behavior explicit.

How the interaction works

Submitting the planner form reads its selected values with FormData and looks up a sample result. Text is placed into the page with textContent, while list items are built as elements, so user-entered notes are displayed as text rather than interpreted as HTML. Notes are saved in this browser. A chosen image uses a temporary object URL for preview and is never uploaded or analyzed.

Frontend concepts

  • Data lookup maps form selections to a predictable interface state.
  • Safe DOM updates keep user text out of HTML parsing.
  • Object URLs let a page preview a local file without sending it to a server; the URL is revoked when cleared or replaced.
  • Sample rules keep the interface usable without API keys or network services.

Limits and next step

The results are illustrative sample rules, not validated crop recommendations. Soil and water choices do not affect the crop selection in the current sample table. Any real guidance requires verified local agronomy data, expert review, and careful handling of uncertainty before it is presented as advice.

04 · PRODUCTIVITY

Focus Board

A small task planner for practising list updates, filtering, date labels, and browser persistence.

Open the demo ↗

Starting point

This is a new project in the collection. The goal is to make a few everyday task actions visible and easy to try without introducing a framework or remote service.

How the interaction works

Tasks live in a JavaScript array and are rendered as DOM elements. Add, complete, delete, and filter actions update that state; changes are saved in localStorage. Saved records are checked for expected fields before use. Progress is recalculated from today’s tasks, and due dates are formatted for display.

Frontend concepts

  • State and rendering are kept together in a small, readable flow.
  • Input values are trimmed and capped before they become tasks.
  • Checkbox and delete controls have accessible names tied to each task.
  • Filters change which tasks are shown without deleting the other tasks.

Limits and next step

Tasks stay in one browser profile and are not synchronized or backed up. The next step would be to add explicit empty, error, and storage-unavailable states, then explore a backend only if cross-device accounts were needed.

How to use this collection

These are learning demos. Read each project’s notes and code, try the interactions, and make your own changes before describing the work in an interview. The repository README explains the collection’s background and the AI assistance used to prepare it.
